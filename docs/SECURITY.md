# Security and data integrity assessment

This document is the threat model and security assessment; for the short answer, read **At a glance** and the [Summary](#summary) table below, and for the remaining risks, [§11](#11-residual-risk-summary).

This document covers what CarbonLEI protects, what it trusts, how it can be attacked and what risk remains. It follows the design in [ARCHITECTURE.md](ARCHITECTURE.md). Everything written as a mitigation is implemented in this repository and covered by the tests named in the Test column, unless it is marked **Roadmap**. Test names refer to the Foundry suites in `contracts/test/` and the vitest suites in `sdk/test/`.

Scope: the two contracts on Ethereum Sepolia, the SDK verification pipeline, the vLEI off-chain service and the hosted demo.

**At a glance.** CarbonLEI protects who signed a CBAM verification report, whether the body and its auditor were authorised at the block that registered it (as far as the watcher has synced revocations, with a 24-hour CONTESTED window), and that its verified tonnage is claimed only once within this deployment, per credential, across importers (a second report for the same installation and reporting period reverts with `PeriodAlreadyCovered` unless it names the report it supersedes); it does not prove that the measured emissions are correct. The largest residual risks are the physical origin of goods within the verified tonnage (T6), the single allowlist owner key, which can add entries, replace a body's address and hand over ownership (T10), period squatting and takeover between accredited bodies (T19), reports falsified by a body, which have no on-chain closing path (T3), volume visibility on-chain (T15), and the prototype's vLEI checks, which verify the issuers' and witnesses' signatures in the presented key event logs but use exported evidence and query no witnesses (§4.1). Each threat in §4 names the tests that cover it, §5 gives the test and static-analysis results, §9 states the security properties P1–P6 and what checks each, and §11 gives the residual risk levels.

## 1. Security goals

| Goal | Meaning | Main control |
|---|---|---|
| Authenticity | The report was issued by the verification body named in it | On-chain registration is authenticated by `msg.sender`, which must be the current address of an active body. The EIP-712 signature by the same address makes the credential portable, so anyone can check the issuer offline (check 3). Check 4 compares the on-chain `verifier` with the signed `core.issuer.verifierAddress` |
| Authority | The signer was an authorised lead auditor of an accredited body at signing time | ECR and accreditation credentials, checked off-chain on exported vLEI evidence (check 7, limits in §4.1). On-chain: `isAuthorizedAt` at the registration block, which reflects the allowlist operator's assertion and evidence hashes, not a proof |
| Integrity | Disclosed values are exactly the values signed | Salted digests and SAID (checks 1–2) |
| Single use | Verified tonnes are claimed at most once | Tonnage ledger and batch uniqueness in `EmissionsClaimRegistry`. Across reports for the same installation and period: a two-level key (`reportScopeKey`, `credScopeKey`) allows one report per installation and reporting period, revised only by a superseding report, and carries the claimed quantity across revisions; the ledger slot is the pair of both keys (T19) |
| Confidentiality | The importer sees only what the supplier discloses | Selective disclosure; no field values on-chain |
| Timely revocation | Revoked authority stops new reports; earlier reports keep their status | WATCHER role with its own key; one watcher process syncs ECR revocations automatically, and suspensions are sent manually with the watcher key. Block time orders the registration transaction against the revocation-sync transaction, not the KERI events. Reports registered within 24 hours before a sync are marked CONTESTED (T2) |
| Independent verifiability | Anyone can re-run the checks | Open-source SDK and CLI, public contracts with source verified on Etherscan, recomputable evidence |

What CarbonLEI does **not** prove: that the emissions measurement itself is correct. It proves who signed it, whether they had authority, and that the tonnage is used once.

Check 8, a rule-based report–credential consistency check (rule set `carbonlei-reconciliation/1`, 12 rules), compares the structured fields of the signed verification report with the credential and checks them against the regulation. It produces three hashes (input, output and rule version) that are part of the credential core, so the SAID, the body's EIP-712 signature and the auditor's KEL anchor all cover them. The reconciliation itself only raises warnings, it uses no AI model, and it does not show that the measurement is correct either. Check 8 also runs sub-rules on the verification report itself (rule set `carbonlei-verification-rules/1`, `sdk/verification-rules.ts`, §4.5): the report must not be dated before verifiers could issue reports (January 2027) nor before its reporting period ended, the accreditation must be valid on the report date, and the first verified period needs a physical site visit unless Art 4 of IR (EU) 2025/2546 applies. A breach in the auditor-signed report fails check 8 (INVALID); anything that needs a person's judgement is a warning. When the core carries the three hashes but the presented extract is missing, changed or partly hidden, check 8 is not decided and the result is INCOMPLETE, never VALID. They are not in the signed rule set, so every credential already issued keeps verifying.

## 3. Trust assumptions

1. GLEIF and QVIs issue LE vLEIs correctly. In the prototype the GLEIF root is simulated locally with test keys.
2. The NAB issues and revokes accreditation credentials in line with its real accreditation decisions.
3. The verification body issues ECRs only to its lead auditors and revokes them when they leave.
4. The lead auditor's verified values are correct. CarbonLEI does not replace the verification itself.
5. Ethereum consensus provides ordering and block timestamps accurate to seconds. Sepolia is a public testnet and is used for the prototype only.
6. KERI witnesses: fewer than the receipt threshold are malicious (prototype: 3 witnesses, threshold 2, all run in one local container) [5]. In the demo the 3 witnesses run in one local container under one operator, so they are a single trust domain and "fewer than the threshold are malicious" does not hold there: whoever controls the container controls all three. Detecting duplicity needs independent witnesses and watchers, which are not implemented (T12).
7. keccak256, SHA-256 and Blake3 are collision-resistant; secp256k1 ECDSA and Ed25519 are unforgeable for classical attackers (see §10 for quantum attackers).
8. The allowlist owner performs the off-chain checks before adding an entry; in the prototype `verifier/src/onboard-check.ts` verifies a body's vLEI chain before onboarding and rejects the demo impostor; attack 4 shows what a stolen allowlist owner key that skips this check can do (T10). The contract records the owner's assertion together with the evidence hashes; it does not verify vLEI facts itself. Check 7 compares those hashes with exported vLEI evidence in the SDK, the CLI and on the hosted page alike. Within the limits in §4.1, every mode therefore still relies on the owner's assertion together with the exported evidence.
9. SAIDs are computed over the compact JSON serialisation of the credential in its original field order (ACDC uses insertion-ordered field maps [6]). Every implementation that recomputes a SAID must preserve that order; a serialiser that reorders keys produces a different SAID, which fails closed as `SAID_MISMATCH` and cannot make a forged credential pass.

### 4.1 Limits of the vLEI checks in the prototype

- **Exported evidence.** Checks 6 and 7 run in every mode (SDK, CLI and hosted page) on KERI evidence exported from the local KERIA agents on 5 October 2026 and carried in, or referenced by, the proof; a referenced authority bundle is bound to the proof by its SHA-256 hash, and its path must name a file under `evidence/` (letters, digits and `_ . / -`, no `..`, no leading `/`); any other path fails check 7 and is never fetched. They recompute SAIDs and verify controller and witness signatures, but do not query witnesses or the issuers' current KELs: the witness receipts are those in the presented evidence. A revocation made after the export is visible on-chain once the watcher syncs it; check 7 reads the auditor's `revokedAt` from the allowlist, and judges it against the registration time.
- **Check 6** checks that the auditor's interaction event at `kelSeq` anchors `credSAID`, that its SAID and size are correct and that its Ed25519 signature verifies with the key in force at `kelSeq`: walked from the auditor's self-addressing inception through the auditor's events #0 to #`kelSeq`-1 in the evidence (`kel`), as in check 7. When `kelSeq` is greater than 1 the evidence must carry them: without them check 6 fails ("the auditor's KEL events #0 to #… are not in the evidence, so a key rotation before the anchor cannot be ruled out"), because a rotation could sit between the inception and the anchor. At `kelSeq` 1 nothing can come between them, and the inception event (`establishmentRaw`) is enough. The anchor event must also follow the state rules keripy applies to it: its `p` is the SAID of event #`kelSeq`-1, and an AID whose inception is establishment-only (`c: ["EO"]`) or that has no next key (a non-transferable inception or an abandonment rotation, `n: []`) cannot anchor; check 7's walk rejects any event after such a rotation too. `s` must be lowercase hex without leading zeros, a second event at the anchor's sequence number fails as duplicity, a rotation may not cut and add the same witness, and the next-key threshold must fit the next keys (one key with `nt` "1", or none with "0"). A malformed `kel` or inception fails check 6 with a reason; it never throws. The anchoring event and each earlier event must carry Ed25519 signatures over their exact bytes from at least the witness threshold (`bt`) of the witnesses in force. The demo proof carries the auditor's events #0 to #2 as `kel`, taken unchanged from the exported evidence (`kel-auditor.json` for #0 and #1, the anchor export of #2); with no rotation the detail reads as before, "witness receipts: 3 of 3 on this event, 3 of 3 on the inception event (threshold 2)". Limits: check 6 queries no witness or watcher, so it does not see a rotation after `kelSeq` that the evidence leaves out (for example a recovery rotation made after a key compromise is found), and a KEL forked before a rotation passes. Someone who holds the rotated-out key can build new events from #0 with it, either a #1' that anchors a new credential (`kelSeq` 1, with or without `kel`) or a whole `kel` (#0, #1', #2', …) for any `kelSeq`, and check 6 accepts them whenever the witness signatures on those events reach the inception's threshold: always for an AID without witnesses (`bt` 0), and also when the witnesses that the rotation removed, or any other colluding witnesses, number at least the inception's `bt`. Nothing in the presented evidence shows the real rotation; only an evidence set that also carries the real rotation fails ("another event at #1"). Detecting such a fork needs a query to the auditor's witnesses or to a watcher for the current key state, which this project does not do. (Second red-team round, 7 October 2026; the earlier downgrade, a cut KEL signed with the old key and receipts borrowed from a witness still in office, now fails.) The rotation tests use a test identifier's KEL made by keripy 1.2.13 (`sdk/test/fixtures/kel-rotation/`); the establishment-only and abandoned cases use two test identifiers made by keripy and interaction events keripy rejects (`sdk/test/fixtures/kel-states/`).
- **Check 7** recomputes the SAIDs of the five credentials (QVI, body LE, NAB LE, accreditation, ECR), follows issuer, holder and edge links, checks the LEIs, the role name, the CN scope of the accreditation, its schema (the CBAM accreditation schema pinned in `sdk/vlei.ts`, not the schema the evidence names), that its `validUntil` is present and covered the registration time, that each credential has an issuance event and an anchoring event in the exported stream, and that the allowlist's LE, accreditation and ECR hashes equal the SAID hashes. Authority is judged at registration, as in check 4: from the allowlist records read at the verified block (the fields used never change, except `revokedAt`, which is set once), the auditor was added at or before the registration time and not revoked before it (a revocation in the registration's own block came after the registration, which would otherwise have reverted; check 4 shows it as CONTESTED), and the registration time is not after `accreditedUntil`. A TEL revocation (`rev` or `brv`) in the evidence counts only when its SAID and size recompute, it is in the credential's registry, follows the issuance, and an event in the issuer's KEL anchors it with the seal { i: credSAID, s: "1", d: revocation SAID }, that KEL verified from inception like an issuance anchor; such a revocation fails check 7 when its `dt` is before the registration time, has no time zone, or there is no registration time, and is named in the detail when it came after registration. Any other revocation in the evidence is ignored. Every time check 7 reads (`validUntil`, `dt`) must be ISO 8601 with a time zone (`Z` or `±hh:mm`); one without a time zone fails, and none is read in the machine's time zone. The root AID is pinned in the verifier configuration (for the demo, `DEMO_TRUST_ANCHOR` in `sdk/vlei.ts`); the QVI credential's issuer is compared with it first, so a chain built under another root fails whatever root the bundle names, as attack 4 shows. For every credential, root first (QVI, NAB LE, body LE, accreditation, ECR), it then checks that the issuer signed the issuance (`sdk/kel.ts`): the SAID of the TEL issuance event recomputes and the event is in the credential's registry; an event in the issuer's KEL anchors that issuance with a seal; walking the issuer's KEL from its self-addressing inception event to that anchoring event, each event's SAID, size, sequence number and link to the prior event are correct, and its Ed25519 controller signature verifies with the key of the latest establishment event; a rotation must reveal the key committed to by the prior next-key digest; every event walked (through the later of the issuance anchor and the registry anchor) carries Ed25519 signatures over its exact bytes from at least `bt` distinct witnesses of the witness list in force at that event (the inception's `b`; a rotation removes `br`, then appends `ba`, and sets `bt` again), where an indexed witness signature at index i is checked against the i-th witness's non-transferable key, a receipt couple counts only for a listed witness, and a duplicate or a key outside the list does not count; and the registry's inception event names the issuer and is anchored in the same KEL. The QVI credential's anchoring event must therefore be signed with the pinned root's own inception key: a chain forged to claim the pinned root fails at the signature step, while attack 4's chain fails earlier, because its QVI issuer is not the pinned root. Limits: delegated identifiers and multi-key or weighted signing thresholds are not supported and fail closed; check 7 uses the presented evidence, witness receipts included, and queries no witness, so KEL freshness and duplicity beyond the presented stream are not detected (a revocation of the QVI, LE or accreditation credential made after the export is not seen by check 7, see T12; the ECR's comes from the allowlist); the SAIDs of nested blocks inside a credential (such as its attributes and edges) are not recomputed separately, only the credential's own SAID, which covers their content. Verifying the receipts raised the time of check 6 from about 4.6 ms to about 23 ms and of check 7 from about 58 ms to about 174 ms (Node, warm average on the development machine).
- **Roadmap:** query the auditor's KEL through witnesses or watchers in check 6, so that a rotation after `kelSeq` and duplicity beyond the presented evidence are seen; pin the GLEIF root AID in production; query KELs and receipts through independent witnesses and watchers at verification time; support delegated identifiers and multi-key thresholds; recompute the SAIDs of nested credential blocks.

### 4.3 Check 9: precursors

Check 9 runs only for a proof whose credential commits to a precursor statement (`precursorDigest` in the signed core) or that carries precursor evidence; for any other proof, including every proof of a credential registered on Sepolia, nothing changes. It is implemented in `sdk/precursor.ts` and verifies the precursor tier with the same code as the good: each producer's proof goes through checks 0–9, against the same block, with check 5 bound to the good's supplier LEI and the good credential's SAID (`precursorBeneficiaryOf`: the producer's claim names the one credential it backs). The formula and the precursor rules follow Commission Guidance No. 3, section 4.2.2.3 and Table 4-2, and Guidance No. 5d, p. 14 [README sources 26, 27].

**Verdict mapping, and why.** The rule is the one the other checks follow: INVALID when a check ran and found the value unsupported, CONTESTED when it needs a person, INCOMPLETE when a check that decides validity did not run, advisory when the value is still supported.

| Check 9 finds | Status, code | Overall | Why |
|---|---|---|---|
| The statement differs from the signed digest, or the signed statement is malformed | fail, `PRECURSOR_INVALID/DIGEST_MISMATCH` or `/STATEMENT_MALFORMED` | INVALID | Tampering, as `DISCLOSURE_TAMPERED` |
| A producer's proof is INVALID: not registered (a body not on the allowlist cannot register), revoked, superseded, signed by another key, its vLEI chain fails, or the batch was not claimed for this maker and this credential (a batch claimed for another credential of the same maker included) | fail, `PRECURSOR_INVALID/CREDENTIAL` | INVALID | The good's value relies on precursor data that are not verified; under the guidance the precursor's default value would apply, and the declared value is not recomputed with it (this verifier has no Default Values Act table) |
| The producer's CN code differs from the statement, is not a relevant precursor (chapters 72/73 for iron or steel products, never 7204 scrap), or its period starts after the good's period ends | fail, `PRECURSOR_INVALID/SCOPE` | INVALID | The credential is real but not for this precursor |
| The tonnes claimed for this maker are below m × the good's verified tonnes | fail, `PRECURSOR_INVALID/MASS_NOT_COVERED` | INVALID | Part of the verified output rests on wire rod with no verified claim behind it |
| Declared SEE below ae + Σ m × SEE by more than 0.01 tCO2e/t | fail, `PRECURSOR_INVALID/SEE_UNDERSTATED` | INVALID | The signed value is lower than its own signed inputs give: the dangerous direction for a buyer |
| A producer's proof is CONTESTED | warn, `CONTESTED` | CONTESTED | Inherited: a person reviews the producer's report first |
| The statement, a producer's proof or a value needed for the recomputation was not presented, or a producer's proof is INCOMPLETE (no evidence checker), or the tree needs more than `MAX_PRECURSOR_NODES` (32) producer verifications, or no check 9 checker was supplied | skipped; warning `PRECURSORS_NOT_CHECKED` | INCOMPLETE | Not run is not a pass, as checks 6 and 7. A supplier may withhold the tier (for example to keep its mill confidential); the result then says so instead of passing |
| A precursor default value is applied | warn, `PRECURSOR_WARNING/DEFAULT_USED` | unchanged | Allowed by the guidance; the value is the body's statement, flagged so a buyer sees it |
| Declared SEE above the recomputation by more than 0.01 | warn, `PRECURSOR_WARNING/SEE_OVERSTATED` | unchanged | Conservative for the buyer, but not what the statement gives |
| Evidence presented for a credential without `precursorDigest` | warn, `PRECURSOR_WARNING/UNSIGNED` | unchanged | Nothing binds it to the good's value; shown for information only, and no producer proof is verified for it (a large unsigned tree costs no chain reads) |

The tolerance (0.01 tCO2e per tonne of good, about 0.5% of 1.8) is ours: SEE values are reported rounded and the guidance sets none. Recursion stops after `MAX_PRECURSOR_DEPTH` (3) tiers; past it, a tier's own check 9 does not run and the result is INCOMPLETE. All tiers together verify at most `MAX_PRECURSOR_NODES` (32) producer proofs per verification (a statement has at most 16 lines, so three full tiers would be 4,368); the lines beyond it are not checked and the result is INCOMPLETE. Before this limit (§15, the fan-out finding), a 2 MB proof with 16 lines over two tiers made one verification send 2,458 JSON-RPC requests. A revised good credential has a new SAID: its producer must claim the precursor batch again for it, and the earlier claim stays counted against the producer's tonnes (conservative). The root of trust for the precursor tiers is pinned like the first (`--precursor-trust-anchor`, default `--trust-anchor`), never taken from the evidence; a test pins the demo root for the mill tier and gets check 7 failing.

**Not covered.** The mass consumed per tonne (m, scrap included) and the screw process's own emissions are the screw body's signed statement; check 9 checks them for consistency, not against the plant. A precursor default is taken as the body states it, not read from the Default Values Act. The wire rod's physical link to the screws is not checked (as T6). The producer's proof discloses the mill's LEI and installation to the buyer (REQUIRED_DISCLOSURES), which a screw maker may not want; check 9 has no selective-disclosure variant for the tier. Weighted averages over several suppliers and production years (Guidance No. 3, p. 35) are expressed as several lines; the verifier does not check that the lines are complete. Shown on a local anvil chain only, with a synthetic vLEI chain for both tiers (verifier/src/precursor-chain.ts: deterministic test keys, no KERI agents, a test root that must be pinned explicitly); no credential on Sepolia carries a precursor statement.

### 4.4 Check 10: carbon price paid (draft Art 9 rules)

**Draft implementing act, not adopted — illustrative.** Check 10 runs only for a proof that carries carbon price evidence (`carbonPriceEvidence`); for any other proof nothing changes. It is implemented in `sdk/carbonprice.ts` on the rules of the Commission's working draft implementing regulation on the carbon price paid in a third country (Ref. Ares(2026)4841230, 13 May 2026; feedback closed 10 June 2026; not adopted as of 16 October 2026) [README sources 28, 29]. The independent person is modelled as the draft describes it (accredited under EN ISO/IEC 17029:2019 for activity group LIV, draft Art 9(1) and Annex III; a 5 % materiality level per CN code, Art 16) inside the same vLEI/KERI trust model as the verification bodies: an LE vLEI from the QVI, a NAB accreditation, an ECR for its certification lead auditor, the lead auditor's KEL anchor of the statement, and a registration by the body's allowlisted address.

**Verdict mapping, and why.** As check 9: a proof that carries a carbon price claim stands or falls with it, because the claim is part of what the supplier presents; a supplier who does not want that risk leaves the evidence out, and the emissions value is judged alone.

### 4.5 Check 8 sub-rules on the verification report

Research in October 2026 found two gaps a buyer cannot close from a signature alone. "Certification" or "verification" statements on CBAM data circulate that "at closer scrutiny do not hold up to the CBAM data calculation rules or conform to the CBAM verification standards" (carboneer, source 16); and verifier capacity is scarce: as of 13 October 2026 five bodies were documented as accredited, all established in the EU, and the Commission's list had not been published (source 19; the Commission page says the list "will be published on this page", source 17). CarbonLEI already checked the signer's vLEI role, the body's allowlist status, its NAB-signed accreditation expiry and CN scope at registration (check 7). Check 8 now also checks the report itself.

**Where, and why not a new check.** The sub-rules read the same report extract as check 8's reconciliation, so they live under check 8 (`sdk/verification-rules.ts`, rule set `carbonlei-verification-rules/1`), shown as a list under the check. They are not added to the signed rule set `carbonlei-reconciliation/1`: its rule-version hash is in every credential's core, so changing it would make every issued credential (the Sepolia demo's included) report `PROOF_MISMATCH`. They run at verification time instead. The 8-check list is unchanged.

**Verdict semantics.** A breach that the signed data itself shows is a regulatory violation: when check 8's three hashes match (the extract is the one the auditor reconciled, and the body signed the core that carries those hashes), the sub-rule fails and so does check 8: INVALID. The same breach in an extract of a credential without a signed reconciliation is a warning. When the credential's core does carry the three hashes, check 8 must be decided on the signed extract: an extract that is missing, changed after signing (`PROOF_MISMATCH`: one field added, the date moved), unreadable, or whose reconciled fields the supplier kept hidden leaves check 8 not decided (shown as not run, with no sub-rules listed: none was applied to the signed report, so none is reported as passed) and the overall result INCOMPLETE with the warning `RECONCILIATION_NOT_CHECKED`, never VALID. sdk/verify.ts recomputes the hashes itself, so this holds whatever checker ran check 8. (Before our own AI-run review of 17 October 2026, §15 finding 6, adding a field, moving the date or dropping the extract turned a signed breach into a warning and the result stayed VALID.) A finding that needs a person (force majeure, a later-period waiver, the operator's record) is a warning; other check 8 warnings never change the verdict. The Commission-list status is a `note`, information only.

Design choices that reduce attack surface:

- Quantities are stored in kilograms as `uint96`; arithmetic is checked, and the claim check is computed in 256 bits before the addition.
- No payable functions, no token transfers.
- Zero values of `reportKey`, scope keys, report ID, supplier, LEI hash, evidence hashes and addresses are rejected at entry, so a zero key can never look like an empty slot.
- Every state change emits an event, but the events alone do not rebuild the state (corrected on 7 October 2026; before, this line said they did): a takeover (path 3) emits only `ReportRegistered`, which does not carry `supersedes`, no event says that the named credential's report scope moved, and `supplierCommit` and `installationCommit` are in no event. An indexer must read `reports(reportKey)` for each `ReportRegistered` (§4.2 CR8); the SDK reads the getters for every validity decision. `ReportSuperseded` carries `credScopeKey` but not `reportScopeKey`; indexers should group events by the record that `reports(reportKey)` returns, not by the `credScopeKey` topic alone.
- `isValidAt(reportKey, t)` checks registration, revocation, supersession, report-level binding and expiry at time `t`; it does not re-evaluate authority, which `registerReport` checked once at registration. Check 4 passes the shipment's `claimedAt` as `t` when check 5 binds the shipment to the verifier's EORI, otherwise the time of the pinned block (T4; `isValid` uses the current time). `shipmentStatus.reportValid` is simply "not revoked": the claim was validated with `isValid` when it was made, and afterwards only `revokeReport` changes it. A later revocation of the auditor or suspension of the body does not retroactively invalidate earlier reports; this is intended. Revoking the report itself does, for all its shipments.

**Redeployment procedure**

The contracts cannot be upgraded. A defect is fixed by deploying new contracts:

1. Deploy new `VerifierAllowlist` and `EmissionsClaimRegistry`, verify the source on Etherscan, and list the new addresses in the README next to the old ones, with the date and the reason.
2. The EIP-712 domain changes, because `verifyingContract` is now the new `EmissionsClaimRegistry` address. Credentials signed for the old contract do not verify against the new one; this is the replay protection of T4 (c) working as intended.
3. Re-create the allowlist entries on the new contract with the same evidence hashes (LE, accreditation and ECR SAID hashes). Anyone can compare them with the events of the old allowlist.
4. By default, existing reports stay on the old registry contract. The watcher suspends every body on the old allowlist, so no new reports can be registered there. The old contracts have no pause function, so this is read-only for new registrations only: existing reports keep their tonnage ledger and shipments there, and each credential is checked against the registry contract named in its EIP-712 domain.
5. A report moves to the new registry contract only if no shipment has been claimed against it: the body revokes it on the old contract, re-signs it for the new domain and registers it again. A report with claimed shipments is not moved, because revoking it would mark those shipments invalid and re-registering it would start a second tonnage ledger (T19).

The prototype has been redeployed once, on 5 October 2026, with unchanged contract source and not because of a defect, so that the demo credential could carry its reconciliation proof. The first deployment's addresses and records are kept in `contracts/deployments/archive/11155111-v1.json`.

**Why the contracts are not upgradeable**

We deliberately use no proxy and no upgrade function. Whoever holds an upgrade key could change the ledger rules or the stored tonnages after reports are registered. That is the kind of single-operator power T10 tries to limit, and every importer would have to trust the holder of that key. Without a proxy, the source verified on Etherscan is the code that runs, and the contracts stay small enough to review. The cost is the redeployment procedure above.

**Across importers.** Every importer that receives a presentation of the same credential sees the same `credSAID`, and so the same `reportKey`, the same `supplierCommit` (one `idSalt` per credential) and the same EIP-712 signature, whichever fields are disclosed to each. Two importers who compare their presentations can therefore tell that they buy against the same report from the same supplier. A separate credential per importer would avoid this; it is not implemented.

All salts (disclosure salts, `idSalt`, `batchSalt`, `importerSalt`) are 256-bit random values.

No personal names, postal addresses or emissions values are stored on-chain. The auditor's name is inside the ECR, which uses the vLEI privacy mode (salted `u` fields).

Roadmap for linkability and volume privacy: a fresh supplier address per report, commitments with range proofs or zero-knowledge proofs of the ledger invariant, or a permissioned chain for the ledger with public anchoring of its state root.

### 7.1 Personal data

This is our reading of the GDPR, not a legal opinion. No data protection impact assessment has been done, and no role under the GDPR (controller, processor) has been assigned to any party. The deployed demo writes only test identifiers of fictional people.

**What is on-chain and relates to natural persons**

| On-chain item | Whose | Form |
|---|---|---|
| `auditorAidHash` | The lead auditor, a natural person | `keccak256(bytes(auditorAID))`, unsalted (`auditorAidHashOf` in [`sdk/commitment.ts`](../sdk/commitment.ts)). Stored in every report record and in the allowlist's auditor entries, and emitted in `AuditorAdded` and `AuditorRevoked` events |
| `importerCommit` | An importer that is a sole trader, whose EORI number identifies a person | Salted commitment, 256-bit `importerSalt` kept off-chain in the presentation |
| `supplier` address | A supplier that is a sole trader, if its wallet is ever tied to it | Clear EVM address (see the table above) |

**Why `auditorAidHash` is likely personal data.** Article 4(5) GDPR defines pseudonymisation as processing personal data so that it can no longer be attributed to a specific person without additional information kept separately; Recital 26 says that pseudonymised data which could be attributed to a natural person by the use of additional information should be considered information on an identifiable natural person [13]. The additional information here is easy to obtain: the auditor's AID is the prefix of a KEL that its witnesses serve, it is in the signed core of every credential the auditor anchors (`issuer.auditorAID`, which check 4 hashes and compares with the on-chain value), and the ECR binds that AID to the person. Anyone with one proof can therefore recompute the hash and find every report of that auditor on-chain. The EDPB's Guidelines 02/2025 on processing of personal data through blockchain technologies (version 2.0, adopted 7 July 2026) say that a hash of personal data stored on a blockchain is still personal data, and that unsalted or unkeyed hashes should in general not be considered sufficient to protect personal data stored on a public blockchain (§52) [14].

**Why it is there.** At registration the contract checks that the auditor is authorised for the body (`isAuthorizedAt(auditorAidHash, verifier, t)`), and the watcher revokes an auditor by this hash (`revokeAuditor`). That is what lets an ECR revocation stop new registrations on-chain (T2), and what lets check 4 compare the registered auditor with the signed credential (T13).

**Mitigations**

- Implemented: the supplier LEI, installation ID, batch ID and importer EORI go on-chain only as salted commitments with 256-bit salts held off-chain (§7 table), which is the hashing measure the EDPB describes (§52) [14]; the EDPB still treats such a hash as personal data. The auditor's name is only in the ECR, off-chain, in the vLEI privacy mode.
- Design options, **not implemented**; each needs a redeployment and has a cost:
  1. *Keyed auditor hash.* Store `keccak256(auditorAID, salt)` with a salt per deployment. Without the salt, the on-chain value no longer links to the public AID. But every verifier needs the salt for check 4, so it travels in every proof; the value still links all reports of one auditor; and deleting the salt later does not unlink it for the verifiers that kept it.
  2. *No person identifier on-chain.* Keep auditor authority in the off-chain vLEI check (check 7) only, and drop `auditorAidHash` from the contracts. The contract would then no longer refuse a registration by a revoked auditor, and T2 would be caught only off-chain.
  3. *Permissioned chain.* Run the ledger on a permissioned chain whose reading is limited to participants, the option the EDPB says organisations should favour (§40) [14], with public anchoring of its state root (roadmap above). It limits who can read the hash; it does not make it erasable.

**Residual issue: erasure.** A value written to a public chain cannot be deleted. The EDPB observes that actual deletion of personal data stored directly on a blockchain might be technically impracticable; it asks controllers to make sure such data can be rendered anonymous on an erasure request, which presupposes that off-chain data allowing identification is erased, and advises against registering personal data on a blockchain in hashed form (§§103–104) [14]. In CarbonLEI the data that links `auditorAidHash` to a person (the AID in the auditor's KEL and in every proof already issued) is held by many parties, so that condition cannot be met in the current design. This is open; we do not claim GDPR compliance.

## 8. Data integrity chain

```
field value ─(salt, SHA-256)→ disclosure digest ─(sorted list)→ core ─(Blake3)→ credSAID
credSAID ─→ EIP-712 signature (verification body)
credSAID ─→ KEL seal at kelSeq (lead auditor)
credSAID ─(keccak256)→ reportKey on Sepolia ─→ tonnage ledger, validity, shipments
precursor statement ─(keccak256, canonical JSON)→ precursorDigest in the core ─→ credSAID (check 9)
producer's claim for the good's credential: importerCommit = keccak256(abi.encode("<maker LEI>/<good credSAID>", salt)) on the producer's reportKey
```

Changing any field breaks every later link.

**Why the credential carries an EIP-712 signature.** The contract does not verify the EIP-712 signature: on-chain registration is authenticated by `msg.sender`, which must be an active body on the allowlist. The signature serves the holder instead. It makes the credential portable: a supplier can hand it to an importer or a later reviewer, who can recover the issuing body's address from the credential alone (check 3), without an RPC connection. When the chain is queried, check 4 ties the two together: the on-chain `verifier` must equal the signer. The domain (name `CarbonLEI`, version `1`, chain ID 11155111, `EmissionsClaimRegistry` address) binds the signature to that chain and contract, so it cannot be replayed on another chain or contract (T4 c).

## 9. Security properties

This section states the six properties CarbonLEI relies on as semi-formal statements. For each one it gives the statement, the assumptions, the code that enforces it and the tests that check it. A fuzz or invariant test samples call sequences, and a unit test checks one case; neither is a proof. The Halmos checks of §9.2 cover every value of their symbolic inputs, but only for fixed call sequences of one to five transactions from a fixed starting state (and, in one P1 check, storage keys from a finite set): they are proofs within those bounds, not over all call sequences.

**Notation.** σ is the state of `EmissionsClaimRegistry` and `VerifierAllowlist` after any finite sequence of successful transactions. A ledger slot is a pair (s, c) of `reportScopeKey` and `credScopeKey`; in σ it holds `claimed(s, c)` (`credScopes[s][c].claimedKg`) and `latest(s, c)` (`credScopes[s][c].latestReportKey`). For a report key k, `verified(k)` is `reports(k).verifiedKg`. `now` is the block timestamp of the transaction in question.

**Assumptions** used below:

- **A-Hash**: SHA-256, Blake3 and keccak256 are collision- and second-preimage-resistant (§3 assumption 7). For P5, SHA-256 is modelled as a random oracle.
- **A-Sig**: secp256k1 ECDSA (EIP-712) and Ed25519 (KERI) are unforgeable for classical attackers (§10 for quantum attackers).
- **A-RNG**: salts come from `newSalt` (32 bytes from a cryptographically secure generator), are independent per field and are never reused. `buildCredential` also accepts caller-supplied salts, which the test vectors use; issuing tools must not.
- **A-Chain**: Ethereum executes the contracts as compiled, orders transactions, and block timestamps are positive and accurate to seconds (§3 assumption 5).
- **A-Owner**: the allowlist owner adds only bodies and auditors whose vLEI evidence it has checked (§3 assumption 8, T10).
- **A-Watch**: the watcher records an off-chain revocation on-chain within δ of the KERI event, with δ = 24 h by default (`contestedWindowHours`) (T2, T18).
- **A-KERI**: fewer than the receipt threshold of witnesses are malicious, and pre-rotation protects the next key (§3 assumption 6, T11, T12). In the demo the 3 witnesses run in one local container, a single trust domain, so the witness part of this assumption does not hold there; duplicity detection needs independent witnesses and watchers (not implemented). Pre-rotation protects only a next key that has not been revealed yet; checks 6 and 7 walk the KEL and reject a key that a later rotation replaced, but they cannot detect a fork of the KEL without independent watchers (T11). The security argument for these KERI properties rests on the designer's own white paper [9] and the specification [5]; we found no independent formal analysis of KERI, for example in ProVerif or Tamarin, in the literature we searched (arXiv, IEEE, ACM and Springer, October 2026).

### 9.3 Protocol model (Maude)

**Result: a bounded model check of an abstract model of the protocol found no violation of the properties below, and no violation that §4 and §11 do not already describe; its CR1 part finds the attack on V1, on V2 without the monitoring that §13.1 requires, and, since its extension to WATCHER grants and lifts on 14 October, on V2 when an owner key that is not behind a timelock first removes the watcher, even if the body watches (a finding against the V2 code, which is not deployed; §13.1).** The model (`formal/maude/carbonlei.maude`, rewriting logic, Maude 3.5.1) covers the allowlist with suspension, the ECR revocation in KERI, the watcher that mirrors it on-chain, registration and the tonnage ledger, claims, and the verifier's verdict from checks 4, 5 and 7 with the CONTESTED window. Maude's `search` explores every reachable state of each instance, and its LTL model checker checks four temporal formulas, three of which hold by construction of the model and serve only as sanity checks, not as security claims. This is not a proof that the protocol or the code is secure: the model is a hand-written abstraction, and its correspondence with the code is listed line by line in [formal/maude/README.md](../formal/maude/README.md#model-and-code). A separate, smaller model of CR1 (module `CARBONLEI-CR1`) checks a thirteenth property against the V1 and V2 rotation and revocation rules (last bullet but one). ## 10. Post-quantum note

- **Today's signatures are not post-quantum safe.** Ed25519 (KERI AIDs created with signify-ts) and secp256k1 ECDSA (Ethereum accounts, EIP-712) can both be broken by a large enough quantum computer running Shor's algorithm.
- **Pre-rotation is not by itself a post-quantum migration path.** A next-key digest commits to one specific key, and in every KEL of the prototype that key is an Ed25519 key: `sdk/kel.ts` computes the digest as Blake3-256 over the key's qb64 text, accepts a rotation only if the revealed key hashes to the prior digest, and decodes only Ed25519 key codes. Moving an AID to a post-quantum suite would therefore take at least one more Ed25519 rotation whose next-key digest commits to a post-quantum key, and then a second rotation that reveals and uses that key; until then the AID is controlled by Ed25519 keys. That second step needs a CESR code for a post-quantum key and signature, and there is none: as of 24 September 2026, neither keripy (main branch, v2.1.0-dev1; latest release 1.3.6) nor signify-ts implements a post-quantum signature suite, keripy signs with Ed25519 and ECDSA (secp256r1, secp256k1) only, and the CESR code table defines no post-quantum signature codes (post-quantum operations are an open issue in the CESR specification). The verifier would also need a post-quantum verification path: checks 6 and 7 verify Ed25519 only. What pre-rotation does protect is a next key that has not been revealed yet: only its digest is public, so a quantum attacker cannot derive it from a public key. Once a key has been revealed in a rotation it is as exposed as any other Ed25519 public key. Pre-rotation also does not help against a current key that is already compromised: until the controller rotates, that key can still anchor fake reports (T11).
- **Ethereum account signatures** remain a dependency. Migrating Ethereum itself is outside the scope of this project.

### 10.1 Harvest now, forge later

An attacker can record every presentation, KEL export and transaction today and wait for a quantum computer that breaks Ed25519 and secp256k1. What that attacker gains differs for three kinds of data.

- **Anchored history.** Every Ed25519 key that has signed a KEL event is public in the KEL, and witness AIDs are their own public keys. Once Ed25519 is broken, the attacker can derive those private keys and sign another version of a KEL: another event at the same sequence number, a KEL without a revocation, or new credentials, each with a full set of witness receipts. Checks 6 and 7 would accept such a version, because they check signatures, not which version was seen first. The EIP-712 secp256k1 signatures fail at the same time: the address of every body that has sent a transaction reveals its public key, so the attacker can sign credentials, and send transactions, as that body (check 3). The on-chain record does not repair this. `registeredAt`, `auditorAidHash` and `kelSeq` prove only that at a given block a report with this `reportKey` was registered naming that auditor and that sequence number; no digest of the KEL event is stored, so they do not prove what the KEL contained, and a forged KEL whose event at `kelSeq` anchors the same `credSAID` matches them. What stays bound is the credential content: `reportKey` is the hash of `credSAID`, which commits to every field, so changing a registered credential's values needs a new registration.
- **New reports not yet signed.** Nothing in the prototype protects them once the keys can be forged: they would need post-quantum signatures from the start, in KERI and for the credential signature.
- **On-chain hashes.** keccak256 commitments, `reportKey`, salted commitments and next-key digests keep their binding. Grover's algorithm speeds up pre-image search only quadratically, which leaves 256-bit digests with about 128 bits of pre-image security; the salts are 256-bit for the same reason. Collision search does not pose a practical threat to 256-bit digests (SHA-256, Blake3, keccak256): the Brassard–Høyer–Tapp algorithm needs fewer hash evaluations than classical search, but Bernstein [11] shows that once hardware and memory are counted, all known quantum collision algorithms are less cost-effective than classical parallel collision search.

**Transition options (Roadmap, not implemented).** (a) Hybrid signatures: the body signs the credential core with both secp256k1 (EIP-712) and a post-quantum scheme such as ML-DSA (FIPS 204 [15]), and verification requires both; on the KERI side, a two-key AID with one Ed25519 and one post-quantum key once CESR defines codes, which also needs the multi-key support the prototype lacks (§4.1). (b) Re-attestation: while Ed25519 and secp256k1 are still sound, re-anchor the `credSAID` of every report still in use with post-quantum keys and record the new attestation on-chain, so its validity no longer rests on classical signatures alone. (c) Store a digest of the anchoring KEL event on-chain at registration (a contract change), so that the record pins the KEL content and not only `kelSeq`. Interface draft, not implemented: [§13.2](#132-post-quantum-migration-path).

## 12. Future: on-chain verification of KERI signatures

Today CarbonLEI anchors in KERI and records `(auditorAidHash, kelSeq)` on-chain; KERI signatures are verified off-chain. Direct on-chain verification is on the roadmap.

- Sepolia has the P-256 verification precompile from EIP-7951 at address `0x100`. We verified it on 2026-09-23 with `eth_call`: a valid signature returned 1 and a tampered one returned empty output [2].
- signify-ts's built-in signer generates Ed25519 keys only. Its verifier can check P-256 signatures, and its key manager accepts external key modules; secp256k1 is not supported [3]. So an auditor AID created with the default signify-ts keys cannot be checked with the P-256 precompile today; a P-256 AID would need an external key module, such as a hardware key.
- There is no Ed25519 precompile on Ethereum (EIP-665, which proposed one at 2,000 gas, is stagnant) [4]. Verifying Ed25519 in Solidity is orders of magnitude more expensive than a precompile call: one published estimate, from a Solidity implementation (Rainbow Bridge), is about 500,000 gas per signature [12], against 3,000 gas for the `ecrecover` precompile.
- Path: a P-256 AID (for example from a hardware key) plus the EIP-7951 precompile would let a contract check an auditor's signature once at onboarding. The contract would still need a trusted view of the KEL key state, so the KEL anchor and watcher stay in the design.

### 13.1 CR1: rotation and revocation by a freshly installed address

**Status: implemented and tested in `contracts/src/v2/`, not deployed; the live demo uses V1.** `VerifierAllowlistV2.sol` and `EmissionsClaimRegistryV2.sol` are new files. The deployed sources `contracts/src/VerifierAllowlist.sol` and `contracts/src/EmissionsClaimRegistry.sol` are unchanged, so the Etherscan-verified source and the on-chain audit still describe the code that runs. No V2 contract has been deployed. The demo and the SDK's verification (`verify`, checks 1–8) have not been run against V2; only the V2 monitor (`verifier/src/watch-v2.ts`) and the SDK's read helpers (`sdk/v2.ts`) have, on a local anvil chain in tests.

Goal: a stolen allowlist owner key can no longer move a body to its own address and invalidate the body's reports at once, by revocation, supersede or takeover (T10, CR1); it needs `ROTATION_DELAY` plus `REVOKE_HOLD` without the body or the watcher reacting. As first written, V2 met this only for revocation: our own AI-run review found ways round it through a second, self-consented rotation, a self-granted watcher, and supersede/takeover (Review findings and fixes, below), now closed. The interface as implemented:

```solidity
// VerifierAllowlistV2: rotateVerifierAddress is removed; every V1 view and event keeps its signature.
uint64 public constant ROTATION_DELAY = 72 hours;
function proposeRotation(bytes32 leiHash, address newAddr) external onlyOwner;      // emits RotationProposed(leiHash, newAddr, readyAt = now + ROTATION_DELAY)
function cancelRotation(bytes32 leiHash) external;                                   // the body's current address, WATCHER_ROLE or the owner
function executeRotation(bytes32 leiHash) external;                                  // anyone, once block.timestamp >= readyAt
function executeRotationSigned(bytes32 leiHash, bytes calldata oldAddrSig) external; // anyone, without the delay, if the current address signed
                                                                                     // EIP-712 Rotation(leiHash, newAddr, nonce) (EOA or ERC-1271 wallet)
                                                                                     // and was bound at least ROTATION_DELAY ago (review fix H1)
function proposeRoleGrant(bytes32 role, address account) external;  // admin (= owner), WATCHER_ROLE only; grantRole(WATCHER_ROLE, ..) reverts (H2)
function executeRoleGrant(bytes32 role, address account) external;  // anyone, ROTATION_DELAY after the proposal
function cancelRoleGrant(bytes32 role, address account) external;   // any current WATCHER or the owner

// EmissionsClaimRegistryV2: registration and claims are the V1 code, except that a registration that supersedes or takes over
// reverts CallerNotMature from an address bound less than REVOKE_HOLD ago (review fix M1); takeovers emit ReportScopeTakenOver.
uint64 public constant REVOKE_HOLD = 72 hours;
function revokeReport(bytes32 reportKey, uint64 effectiveFrom) external; // applied at once if the caller's address was bound at least REVOKE_HOLD ago,
                                                                         // otherwise queued (RevocationQueued); effectiveFrom <= now, 0 = retroactive as in V1
function executeRevocation(bytes32 reportKey) external;                  // anyone, REVOKE_HOLD after the request, if the requester is still the body's active address
function cancelRevocation(bytes32 reportKey) external;                   // WATCHER_ROLE (read from the allowlist) or the issuing body's current address
```

Where the draft left a choice, we took the simplest rule we could defend:

1. **The owner's proposal plus either a mature current address or an uncancelled delay.** Both paths need the owner's proposal. The consent path also needs the signature of the body's current address, and since review fix H1 only of an address bound at least `ROTATION_DELAY` ago. This is not "two independent parties" in every case: an address the owner installed by a rotation becomes able to consent once it is mature, but by then it could also revoke at once, so the watcher must have suspended the body within `REVOKE_HOLD` in any case (as first written, V2 let that address consent at once, H1). The delay path needs `ROTATION_DELAY` to pass with no cancellation by the body, the WATCHER or the owner (the draft did not list the owner; it lets an honest operator withdraw a mistaken proposal). A suspended body's current address cannot cancel (review fix M2), so a stolen body key cannot block the rescue rotation. One proposal per body at a time; `executeRotation` re-checks that the new address is still unbound.
2. **Consent signatures are single-use.** The nonce in `Rotation(leiHash, newAddr, nonce)` is per body and increases on every executed or cancelled rotation, so a signature covers one proposal and one new address. The EIP-712 domain names the V2 allowlist and the chain. Signatures go through OpenZeppelin `SignatureChecker`, which rejects high-s (malleable) ECDSA signatures and accepts ERC-1271 wallets.
3. **What counts as "freshly installed".** The hold reads the existing V1 field `leiOfAddress(addr).boundAt`: any address bound less than `REVOKE_HOLD` ago, including a new body's first address in its first 72 hours. This needs no new state and no change to the V1 view, at the cost of holding a new body's revocations too.
4. **A queued revocation lapses with its requester.** `executeRevocation` fails if the requester is no longer an active address of the issuing body (suspended, rotated away, accreditation expired); the body's current address can then cancel it. An immediate revocation by a matured address replaces a queued one. During the hold the report stays valid and claimable.
5. **`effectiveFrom` keeps the V1 record shape.** It is stored in a separate mapping, `revocationEffectiveFrom`, so `reports()` returns the V1 struct. `isValidAt(t)` is false for `t >= effectiveFrom`; `shipmentStatus.reportValid` stays true for a shipment claimed before it. A V1 reader that ignores the mapping treats every revocation as retroactive, which is the cautious reading.
6. **Cancelling a held revocation.** The WATCHER, as drafted, and also the issuing body's current address. After a hostile rotation that address is the thief's, which can only cancel its own revocation.
7. **Owner and roles.** `Ownable2Step` (a new owner must accept; `DEFAULT_ADMIN_ROLE`, which administers the WATCHER role, can be held only by the owner and moves on acceptance) and `renounceOwnership` disabled. Since review fix H2, WATCHER_ROLE is granted only in two steps, `proposeRoleGrant` and `executeRoleGrant` after `ROTATION_DELAY`, cancellable by any current watcher or the owner; `grantRole(WATCHER_ROLE, …)` reverts `RoleGrantNeedsDelay`. Revoking the role stays immediate (see below). An ownership transfer is not delayed: it gives the new owner no power the stolen key does not already have, and the monitor alerts on `OwnershipTransferStarted`. The owner is meant to be a multisig behind an OpenZeppelin `TimelockController`; the contract does not enforce that, and a test deploys that shape. No new dependency: OpenZeppelin 5.4.0 as already vendored.
8. **Values.** Both delays are 72-hour constants, a governance choice, not a result of this project.
9. **Supersede and takeover need a mature address (review fix M1).** A registration with `supersedes` set, a revision (branch b) or a takeover (branch c), invalidates earlier reports at once, which is what a revocation does; it reverts `CallerNotMature` unless the caller's address was bound at least `REVOKE_HOLD` ago. Cost: a new body, or a body that has just rotated, waits 72 hours before it can revise a report or take over a scope; registering new reports (branch a) is not delayed.
10. **Claims during a queued revocation (L4).** A queued revocation keeps the `effectiveFrom` given when it was queued, so a shipment claimed during the hold becomes invalid if the revocation is executed (`test_L4_claimDuringHold_invalidOnceExecuted`). We chose not to block claims while a revocation is queued: that would let any freshly bound address freeze a report's claims for 72 hours. Instead `sdk/v2.ts` adds an advisory note to a queued revocation saying that a shipment claimed now becomes invalid if it executes, and the monitor cancels queued revocations nobody expected.

**What V2 still cannot stop**

- **Nobody watching.** If neither the body nor the watcher reacts, a stolen owner key completes the attack: the rotation after `ROTATION_DELAY`, the revocations `REVOKE_HOLD` later, 144 hours after the first event (`test_CR1_V2_residual_nobodyWatches_completesAfterBothDelays`). The delays only help a party that monitors `RotationProposed` and `RevocationQueued` and acts within the window. A monitor now exists, `verifier/src/watch-v2.ts` (`npm run watch:v2`, [OPERATE](OPERATE.md#incident-procedures)): by default it cancels every rotation proposal the body has not confirmed (a list of expected rotations in its config), suspends the body after a rotation that was neither expected nor consented by a mature, untainted old address, and cancels unexpected held revocations; the Maude CR1 model shows that cancelling and suspending in time suffice against the rotate-then-revoke attack it models, and nothing more. Since the review it also cancels unexpected watcher-grant proposals, re-imposes a suspension it made if another address lifts it, and alerts on new bodies, auditors, ownership transfers, supersedes and takeovers; those rules are tested on a local chain. Since 14 October the Maude model includes the grant cancellation (needed: a granted account lifts the suspension in the block of the revocation, so re-suspending after the lift comes too late); the alerts are outside it. It is tested on a local chain only (above) and is not deployed or running anywhere, because V2 is not deployed. Even running, it does not help if the monitor and the body are both down for more than 72 hours (the rotation executes and, `REVOKE_HOLD` later, the thief's address revokes at once), or if the watcher key is stolen too (next bullets).
- **Revoking the watcher role is not delayed.** Granting it is (review fix H2), but an owner key that is not behind a timelock can first revoke the watcher's role (`test_CR1_V2_residual_ownerKeyAlsoRemovesWatcher`). We wrote here that the body itself can then still stop the rotation. The Maude CR1 model, extended to role grants and lifts on 14 October, shows that it cannot: the same key proposes WATCHER_ROLE for an account of its own, which nobody left can cancel, uses it 72 hours later to suspend the body, and a suspended body's address cannot cancel a rotation (M2); the attacker's watcher then lifts the suspension and its rotated-in address revokes, 216 hours after the first event (`test_CR1_V2_residual_ownerKeyRemovesWatcher_selfGrantedWatcherBlocksBodyCancel`, finding C1 below). So with an owner key that can revoke the watcher at once, V2 gives no on-chain protection against this attack: only the 72-hour windows in which people can respond off-chain. The monitor raises a `watcher_role_missing` alert on its next poll but can no longer cancel or suspend. With a `TimelockController` owner, the role change waits for the timelock too and a separate canceller can stop it (`test_timelockOwner_stolenProposer_guardianCancels`, `test_timelockOwner_rotationTakesTimelockPlusRotationDelay`, `test_timelockOwner_formerOwnerKeyPowerless`). What remains then is a stolen signing quorum of the multisig while the canceller is absent or also compromised.
- **Griefing and other owner powers.** A stolen owner key can propose again after every cancellation, and the body must keep cancelling (tested over three rounds). It can still add fake bodies and auditors at once (T10, attack 4); V2 delays those only if the owner is a timelock. Since review fix M1 a fake body cannot supersede or take over another body's reports in its first 72 hours, and only while that body is suspended or past its accreditation; the monitor alerts on every body and auditor not in its expected lists but does not block onboarding.
- **A compromised watcher** can cancel honest held revocations and honest proposals, so honest work has to be repeated (T10).
- **A long-held body key (CR1a, T13).** A stolen key that the body has held for longer than `REVOKE_HOLD` revokes at once, with `effectiveFrom` 0, as in V1 (`test_CR1a_V2_residual_longHeldBodyKey_revokesAtOnce`).
- **New registrations by a freshly rotated address are not held**, only revocation, revision and takeover (M1); check 6 and the verifier's 30-day tenure rule stay the defence (T10, §4.2 CR1).
- **Rescue after a stolen body key.** The watcher suspends the body; the owner proposes a new address; the stolen key cannot cancel while the body is suspended (review fix M2; before it, the stolen key could cancel every rescue proposal forever, and a LEI cannot be added again); after `ROTATION_DELAY` anyone executes, and the watcher lifts the suspension (`test_M2_suspendedBodyKeyCannotBlockRescue`). The watcher can still cancel a hostile "rescue" proposal. Until the suspension, the stolen key can revoke at once if it is long held (CR1a, above).
- **Costs.** A body that has lost its key waits `ROTATION_DELAY`; an honest revocation, revision or takeover by a new address, or by a new body in its first 72 hours, waits `REVOKE_HOLD`, and the report stays claimable meanwhile; a body's consent to its own rotation counts only once its current address has been bound 72 hours; a new watcher waits `ROTATION_DELAY`.
- **Assurance.** The V2 code has only this project's own tests, Halmos checks, Slither run and our own AI-run adversarial review (below): no outside review and no audit. The V2 monitor reads pending rotations and queued revocations, and `sdk/v2.ts` tells a V2 deployment from V1 and reports a body's pending rotation and a report's queued revocation as advisory information. The SDK's verification does not use them: verdicts are computed as for V1, and `revocationEffectiveFrom` is not read, so a V1 reader treats every V2 revocation as retroactive (decision 5).

### 13.2 Post-quantum migration path

Which signatures are classical today: the body's EIP-712 signature over the credential (secp256k1 ECDSA, check 3); the Ethereum transactions that register reports and claims (secp256k1); and every KERI signature, Ed25519, by controllers on KEL events and by witnesses on receipts (checks 6 and 7). All can be forged by a large enough quantum computer (§10).

1. **KERI.** The KERI specification describes this step: next keys are committed only as digests, and a rotation whose next-key digests commit to post-quantum keys moves the AID to them (its "surprise quantum attack recovery", SQAR) [5]. A hybrid AID would instead hold one Ed25519 and one post-quantum key with a signing threshold of both. Either way needs a CESR code for the post-quantum key and signature, which the CESR specification does not define yet (it lists post-quantum operations as an open issue), multi-key support in the verifier (§4.1), and a post-quantum verification path in checks 6 and 7. Witnesses would rotate the same way.
2. **Credential signature.** The presentation would carry a second signature by the body, for example ML-DSA (NIST FIPS 204) [15], over the same EIP-712 digest, and check 3 would require both the ECDSA and the post-quantum signature to verify. The post-quantum public key would come from the body's KEL, not from the presentation.
3. **Contract.** Ethereum has no precompile for ML-DSA, so the contract would not verify it; it would only pin what the off-chain verifier checks:

```solidity
// ReportInput gains two fields, stored in ReportRecord:
bytes32 anchorEventDigest;   // SAID of the KEL event at kelSeq, so the record pins the KEL content, not only kelSeq (§10.1 (c))
bytes32 pqSignatureDigest;   // hash of the post-quantum signature over the EIP-712 digest; check 3 compares the presented signature with it
```

The registering transaction itself stays secp256k1, as do the owner and watcher keys; a post-quantum Ethereum account scheme is outside this project. Reports registered before the migration keep only their classical signatures; re-attesting them while the classical keys are still sound is option (b) in §10.

## 14. HTTP API (`carbonlei serve`)

`carbonlei serve` ([`sdk/server.ts`](../sdk/server.ts)) adds the project's only network-facing server, run by the importer itself. It changes no check: every endpoint calls the same SDK functions as the CLI. New attack surface, with threats T24–T27 in §4:

- **Exposure.** No authentication and no TLS (T25). Default bind 127.0.0.1; a warning on any other address. Deployment rule: behind the integrator's gateway, which authenticates callers, terminates TLS and rate-limits ([OPERATE › REST API](OPERATE.md#rest-api-carbonlei-serve-deployment-and-security)).
- **Resource limits** (T24): body size, content type, a body deadline (the body is read before a verification slot is taken), a cap on bodies uploading at once, per-request timeout, concurrency cap, lines per batch, records per re-check, header and request timeouts of node:http.
- **Verdict integrity** (T41): what the server computed from proofs (`/v1/verify-batch`, `/v1/recheck`) carries an HMAC binding; `/v1/portfolio` plans only bound input, or caller-supplied verdicts on an explicit opt-in that the plan states. We chose the HMAC over re-verifying in `/v1/portfolio` so that the endpoint stays a pure computation with no chain read; the cost is that bound documents are tied to the server's key.
- **Data minimisation** (T26): no body, EORI, client address or query string in logs; URLs in errors cut to their origin; webhook payloads of `carbonlei recheck` without EORI, proofs or disclosed values.
- **Files** (T27): evidence read only inside the evidence folder, after symbolic links, size-capped, hash-checked.
- **Input parsing**: a body that repeats a JSON key is refused (400), as check 0 refuses a proof that does; the proof is then passed to the verifier re-serialised, so the two readers cannot disagree.
- Not done: no fuzzing of the HTTP layer, no load test, no review by a third party.

## Supplier allocation book

`carbonlei allocate` and `carbonlei present-batch` ([`sdk/allocation.ts`](../sdk/allocation.ts)) let a supplier answer many buyers from one verified report. They add no new trust: no contract change, no transaction (the supplier's wallet still sends each claim), no server. What they add is a local file with personal and commercial data, the allocation book, and threats T32–T34 in §4:

- **The book is a secret** (T32). It holds each buyer's EORI and the per-batch salts of the importer commitments. Outputs (terminal report, `--json`, `share-pack.json`) carry neither; each proof carries only its own batch's salt, as any proof does.
- **Reconcile before sharing** (T33). Proofs should go out only for batches whose on-chain claim matches the book; `present-batch --check` enforces that.
- **One proof per buyer** (T34). Check 5 binds each proof to one EORI, so a forwarded proof fails for anyone else who runs check 5 with its own EORI.
- **File names** (T42): each share-pack file name carries a short hash of the full importer and batch ids, and a pack never overwrites a file.
- Not done: an encrypted book format; signed acknowledgements from buyers; import from ERP sales orders.
